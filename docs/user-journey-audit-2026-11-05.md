# Аудит пользовательского пути CARA

Дата: 05.11.2026. Проверенный коммит: `8807718`.

## Общая память и предпочтения

Следующим этапом добавлены серверная история и настройки помощника. Предыдущая
локальная история браузера заменена общей историей, а не объявлена синхронизацией.

- История хранится в `assistant_memories`: отдельно для аккаунта, автомобиля
  и языка, до 24 сообщений и не более семи дней для каждого сообщения.
  Активный разговор не продлевает срок хранения старых сообщений.
- Сайт и Telegram передают в AI одну серверную историю. История из тела запроса
  старых клиентов не используется как источник общего контекста.
- Чат на другом устройстве читает те же сообщения. История обновляется при
  открытии, возвращении в окно и кнопкой обновления; фонового realtime нет.
- Очистка на сайте и `/forget` в Telegram очищают выбранный чат в обоих каналах.
  Истории других автомобилей/языков, записи машины, напоминания и настройки
  помощника не удаляются. Уже начатое выполнение подтверждённой операции
  очистка истории не откатывает.
- Номер поколения блокирует запоздавшие ответы и старые подтверждения Telegram
  после очистки. Короткая DB-lease сериализует генерации между экземплярами
  приложения без удержания соединения во время вызова AI. Завершённые действия
  записываются как текст результата, а не как выполняемые инструменты.
- Настройки в `assistant_preferences` доступны на странице настроек: подробность,
  приоритет расходов/надёжности и тип поездок. Они принадлежат аккаунту, действуют
  в обоих каналах и меняют инструкции ответов и рекомендаций. Изменения защищены
  номером версии от перезаписи устаревшим браузером.
- Предпочтения не меняют даты ТО, уведомления и правила безопасности. Неизвестный
  тип поездок остаётся неизвестным. Вычитка сохраняет запрошенную подробность.
- Удалённые/просроченные сообщения не возвращаются в контекст. В работающем API
  очистка просроченных данных запускается при старте и каждый час; при чтении
  они исключаются сразу. Восстановление старых резервных копий БД отдельно не
  управляется этим механизмом.
- Исправлено скрытие пользовательских сообщений мобильным стилем `.user`,
  добавлены метки канала и прокрутка к последнему сообщению.

Проверки:

### Перед публикацией

1. Применить миграции `0021_assistant_memory.sql` и
   `0022_assistant_preferences.sql` штатной командой `npm run db:migrate`
   в нужном окружении. В рабочей базе эти команды агентом не выполнялись.
2. Публиковать новый API и frontend согласованно: новый интерфейс ожидает
   `/assistant/history` и `/assistant/preferences`.
3. После публикации отдельно проверить живого AI, хранение между перезапусками,
   связанный Telegram-аккаунт, очистку и доставку напоминаний. Локальные фикстуры
   не доказывают доступность production-провайдеров или оплаченных лимитов.
4. Старые временные Telegram-сессии и незавершённые подтверждения не переносятся
   в общую память. Подтверждения без нового поколения памяти нужно подготовить
   заново. Старый локальный кэш из предыдущего непубликованного этапа не импортируется.

## Исправления после аудита

Ниже сохранены исходные находки для воспроизводимости. После согласования
в рабочем дереве исправлены все четыре P1 и выполнены следующие интеграции:

- Автоматические напоминания ТО проходят настоящую цепочку сервисов и
  PostgreSQL, включая нормализацию дат очереди. Замена масла не сбрасывает ГРМ.
- Подтверждения Telegram покрывают все операции и три языка. Сбой показа
  предварительных данных не оставляет скрытой операции. Списки работ и планы
  представлены понятным текстом; отмена автоматического ТО предупреждает,
  что выключает все уведомления соответствующего регламента.
- Запоздавшие ответы другой машины/старого обновления не меняют текущие данные.
  Частичные сбои видны; при неизвестной базе ТО нет успокаивающей оценки.
- На главной отображаются календарные напоминания и сроки документов с
  переходами к действиям. Автоматические напоминания показывают целевой
  одометр, ведут к сервисной записи и не предлагают некорректное «Выполнено».
- Главная предлагает заполнить недостающий профиль, пробег и обслуживание,
  а также подключить Telegram. После возврата в окно данные перечитываются.
- Зарядка не отправляет флаг полного бака, тип операции учитывает профиль EV.
  Метрики электромобиля показывают кВт·ч, а не фиктивные литры/100 км.
- На сайте доступны прикрепление файла, скачивание, явный запуск OCR,
  просмотр текста, редактирование и подтверждение полей документа.

  версией документа. Повторный OCR не перезаписывает проверенные поля.
  AI получает только подтверждённые поля, а не неподтверждённые догадки OCR.
- Сводка расходов имеет выбор месяца и валюты. Валюты не складываются и не
  ранжируются по несопоставимым номинальным суммам. История профиля доступна в UI.
- На первом этапе веб-чат сохранял до 24 сообщений на устройстве сроком до 7 дней, отдельно
  по аккаунту, машине и языку. Есть очистка и защита от запоздалого ответа.
  Затем этот механизм заменён общей серверной памятью, описанной выше.
- Добавлены отсутствовавшие переводы UK/PL/EN и локализованные названия
  стандартных полей документов. Убраны неподтверждённые статусы «автопилот»

## Приоритетные проблемы

### 1. P1: автоматические напоминания ТО падают до отправки

`ReminderDeliveryStore.claim()` получает строки из raw SQL и приводит объект к
`ClaimedReminder` без преобразования дат. Затем `isCurrent()` вызывает
`job.sourceVersion.getTime()`. Raw-запросы Drizzle возвращают `timestamptz`
строкой: это подтверждено для установленного PostgreSQL-драйвера и PGlite.

При запуске реальной цепочки «масло на 120000 км, интервал 10000 км,
предупреждение за 1000 км, текущий пробег 129500 км» получено:

```text
TypeError: job.sourceVersion?.getTime is not a function
```

Сообщение не отправляется. Захваченная задача остаётся `sending`, а затем может
стать `uncertain`. Наличие правила и галочки Telegram не означает работающую
отправку. Обычные тесты подменяют синхронизацию ТО пустым методом и не ловят сбой.

Исправление: типизированно преобразовать даты raw-результата и добавить тест
реального `MaintenanceReminderSync -> claim -> isCurrent -> send` без подмены sync.

### 2. P1: запоздавший запрос подменяет данные выбранной машины

У `useVehicleData` нет отмены запроса, идентификатора поколения или проверки

Исправление: привязать результат к машине/поколению запроса, сбрасывать данные
при смене контекста, проверять гонку автоматическим браузерным тестом.

### 3. P1: обычное переключение на зарядку создаёт недопустимый запрос

Форма инициализирует `isFullTank=true`. При выборе `charge` значение не

электромобиля форма по умолчанию предлагает бензиновую заправку.

Исправление: отделить поля и значения зарядки от заправки, учитывать тип

### 4. P1: изменение регламента через Telegram ломает подтверждение

`update_maintenance` зарегистрирована как разрешённая операция и исполняется
в сервисе действий, но отсутствует в словаре `operationLabel`. Построение
превью вызывает `labels[operation] is not iterable`.

Подтверждение записывается в `state.pending` до построения текста, поэтому
нельзя ограничиться добавлением подписи: ошибка превью не должна оставлять
скрытое подтверждаемое действие.

Исправление: исчерпывающие типизированные подписи всех операций, создание
pending только после успешного построения превью, тест каждой операции на
всех трёх языках.

### 8. P2: загрузка, OCR и извлечённые факты документов остаются в API

Backend имеет upload, confirm, process, download и хранение извлечённых
полей. В клиентском documents API есть только список, создание метаданных
и удаление; страница не содержит input файла, просмотра полей и проверки
извлечённых данных. Обычный пользователь не может завершить OCR-сценарий.

Исправление: полный поток «добавить файл -> загрузить -> подтвердить ->
распознать с согласием -> проверить факты -> применить выбранное» с понятными

1. Устранить четыре P1-ошибки и добавить регрессионные проверки реальных границ,
   особенно автоматическую синхронизацию ТО без её подмены.
2. Объединить напоминания, сроки документов и состояние загрузки на главной;
   каждому предупреждению дать прямое действие к его источнику.
3. После добавления машины собирать необходимые исходные данные небольшими

   желаемые предупреждения и подключение Telegram. Не выдумывать интервалы.
4. Завершить поток документов и проверку распознанных фактов; использовать
   подтверждённые факты в истории, профиле и рекомендациях с указанием источника.
5. Обеспечить согласованную память/действия помощника между сайтом и Telegram;
   явно отделить сохранённые данные от предположений в разговоре.
6. Дать выбор периода и валюты в аналитике, доступ к истории версий профиля
   и безопасное резюмирование фактов отчётов.
7. Завершить локализацию и измерять прохождение сценариев, а не только
   открытие страниц: первый автомобиль/пробег, записанное ТО, настроенное и
   доставленное напоминание, проверенные факты документа, выполненная рекомендация.
   Не включать VIN, тексты документов и другие лишние персональные данные в метрики.

Критерий готовности: пользователь без знания API может пройти цепочку
«добавил машину -> внёс исходные данные -> записал обслуживание/страховку ->
увидел корректный следующий срок -> получил тестовое уведомление ->
выполнил действие -> увидел обновлённую историю и рекомендации»; при этом
ошибки и неизвестные данные не маскируются зелёным статусом.
